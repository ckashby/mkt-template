02 / Selected architecture

Local Better Auth, shared organization billing

Confirmed stack: Better Auth runs in this Next.js application, including on localhost during development. Neon remains the Postgres database. Use the Better Auth organization plugin and @better-auth/stripe. The organization is the proposed billing and data ownership boundary.

“Local” describes where the auth server runs. It does not replace Neon with a local database. Managed Neon Auth is outside this plan.

Browser + auth client→Next.js + Better Auth plugins→Neon Postgres + Stripe

Identity and organizations

Use the Drizzle adapter. Configure organization() on the server and organizationClient() on the client. Generate the combined schema after enabling plugins. Include organization creation, switching, membership, invitations, and roles.

Sources: Organization plugin · Drizzle adapter.

Billing integration

Add stripe() and stripeClient({ subscription: true }). Enable subscription.enabled and organization.enabled. Use customerType: "organization" and the organization ID as referenceId. Configure authorizeReference.

The plugin manages customers, subscription synchronization, and verified webhooks at /api/auth/stripe/webhook. Source: Stripe plugin.

Database boundary

Use Neon with Drizzle and a transaction capable Postgres connection. Proposed default: pg in the Node.js runtime, a pooled application URL, and a direct migration URL. Keep database access in server modules.

Connection lifecycle depends on the deployment host. Drizzle also documents Neon HTTP and WebSocket drivers.

Application policy

The app owns tenant isolation, entitlement decisions, usage limits, and business side effects. Treat the active organization as UI context. Validate current membership and the requested action before every protected read or write.

Every tenant owned record carries an organization ID. Queries and mutations constrain both the record and organization, including background jobs.

Proposed role policy

This is an application policy to implement and test, not a claim that plugin defaults enforce every rule.

RoleProposed permissions
OwnerManage billing, organization settings, invitations, membership, and ownership transfers.
AdminManage routine settings and invite or remove ordinary members. Cannot grant owner status, remove owners, or manage billing by default.
MemberUse entitled organization features. Cannot manage membership or access billing management APIs.

Protect the final owner from removal or demotion. Require a verified invited email to accept invitations; handle expiry, revocation, and repeat acceptance. Recheck membership after switching organizations or removing a member. Leave optional teams and dynamic custom roles out of the first release.

03 / Proposed data model

Organizations own data and billing

The proposed first flow is an organization subscription. Exact plans and billing intervals remain product decisions. One time commerce and seller payouts are separate extensions.

RecordsPurpose and constraints
Core authGenerate user, session, account, and verification records from the chosen Better Auth configuration. Preserve adapter names and required indexes.
OrganizationsOrganization, member, and invitation records, plus session organization context. Enforce unique membership per user and organization. Keep plugin supplied customer fields in the generated schema.
SubscriptionsUse the Stripe plugin schema as the subscription projection. Link billing to the organization. Avoid a second independently maintained subscription table.
Application resourcesNonnullable organization ID, creator ID for audit, timestamps and domain fields. Index organization plus common filters. Prevent relations across organization boundaries.
Usage and entitlement policyServer controlled plan mapping, explicit limits and organization scoped counters. Never trust editable organization metadata as proof of a paid plan.
Application event receipts and jobsUnique Stripe event/action key, organization reference, attempt state and completion time. These track custom side effects, not the plugin’s subscription writes. Bound retention and redact payloads.
Audit historyRecord actor, organization, action, resource and time for permission, ownership, and billing changes. Retain necessary history when memberships change.

Use reviewed SQL migrations and foreign keys. Disable organization deletion for the initial release; design archival, subscription cancellation, billing retention, and ownership transfer before enabling it.

04 / Implementation sequence

From local sign in to organization billing

Foundation

Configure the local integration

Select compatible stable versions of better-auth, @better-auth/stripe, stripe, drizzle-orm, pg, a validator and migration tools. Lock versions and verify the selected plugin’s SDK and API compatibility.

Create a safe environment template with DATABASE_URL, DATABASE_URL_DIRECT, BETTER_AUTH_SECRET, BETTER_AUTH_URL=http://localhost:3000, STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, plan Price IDs and email configuration. Use a development Neon branch and Stripe sandbox. Document trusted origins and separate production values.

Forward Stripe events locally with stripe listen --forward-to localhost:3000/api/auth/stripe/webhook. Use the listener’s signing secret locally and the registered endpoint’s secret in production.

Done when: a fresh checkout starts with documented local configuration and the plugin webhook receives sandbox events.

Depends on 01

Generate the full schema

Configure the Drizzle adapter and both plugins before schema generation. Set createCustomerOnSignUp: false for the organization only billing policy. Generate the complete auth schema, review its relations, and apply it through Drizzle migrations. Regenerate when plugin configuration changes.

Test an empty database and an upgrade on isolated Neon branches. Seed two organizations with distinct members and data to exercise tenant boundaries.

Done when: auth, organization, and billing records exist with expected indexes, and migrations reproduce the same schema.

Depends on 02

Implement identity and organization access

Build registration, email verification, recovery, sign in and sign out. Add organization creation, switching, invitation acceptance, member management and ownership transfer. Configure email delivery, trusted origins, secure production cookies and durable rate limiting.

Implement the role policy above. The billing authorization callback must check current membership for the supplied organization and allow only enumerated actions for the owner; deny unknown actions. Reject personal billing flows under this organization only policy. Require ownership checks even when a valid subscription or customer ID is supplied.

If Server Actions set auth cookies, use nextCookies() last in the plugin list. Keep all tenant data access behind server authorization.

Done when: organization A cannot access B, removed members lose access, invitations cannot escalate roles, and a final owner cannot be removed.

Depends on 03

Build plugin based billing

Replace the starter with a workspace and billing page. Define trusted plan mappings and organization billing operations. Use subscription.upgrade for checkout and changes, passing the existing subscription ID when modifying a plan. Provide authorized subscription listing, cancellation, restoration and portal entry.

Register checkout.session.completed and customer.subscription.created, updated, and deleted events. Add invoice events for application policy as needed. Use lifecycle hooks or onEvent for custom work. Plugin API and event reference.

Done when: an owner can subscribe in the sandbox, the correct organization receives access, and members cannot mutate billing through direct API calls.

Depends on 04

Make entitlements and recovery explicit

Proposed policy: active subscriptions allow paid features, trials allow only configured trial limits, incomplete subscriptions do not unlock paid access, and cancellation at period end preserves access until expiry. Choose a documented past due grace period before launch.

Recheck entitlements on server mutations. Enforce limits atomically. Add redacted logs, event replay, reconciliation, and an operator procedure for billing mismatches. Keep memberships when paid access expires, allowing owners to recover billing.

Done when: payment failure, expiry, and recovery change access according to policy without deleting organization data.

Depends on 05

Verify the complete flow

Add CI for lint, type generation and checking, build, domain tests, and isolated integration tests. Exercise the matrix below. Document email setup, Stripe event registration, Neon migrations, local listener usage, recovery and production rollout.

Done when: local and staging flows pass, mobile and keyboard interactions work, and organization isolation holds for every protected endpoint.

05 / Billing reliability

One subscription integration, explicit app policy

  1. Separate trusted state from UI intent. Validate current organization membership, billing role, plan and customer/subscription association. Client supplied organization IDs and return URLs are untrusted. Allow only approved origins and local paths.
  2. Preserve the plugin handler. Route webhook requests through Better Auth without consuming or rewriting the request body. Verify invalid signatures fail and environment secrets do not cross between test and live. Stripe webhook requirements.
  3. Keep application effects idempotent. In custom callbacks, deduplicate event/action keys and transactionally enqueue application work. Use stable delivery keys for emails or provisioning. A duplicate event must not repeat a business effect.
  4. Do not assume shared transactions. Plugin writes and application callbacks may commit separately. Inspect the pinned plugin’s callback order and error handling. Test whether failures trigger retries; use reconciliation to recover missed effects even if a webhook was acknowledged.
  5. Read billing state on the server. A success redirect is not entitlement proof. Render pending confirmation when necessary and recompute access from verified subscription state and the application policy.
  6. Exercise concurrent and reordered events. Test repeated upgrade clicks, two owners checking out concurrently, duplicate delivery and old updates after cancellation. Enforce one intended subscription per organization and reconcile current Stripe state before any repair.
  7. Define seat semantics before using seats. Decide whether billing counts purchased seats or active members, when proration occurs, and whether pending invitations reserve capacity. Enforce admission and downgrade limits atomically. Seat billing remains optional.
